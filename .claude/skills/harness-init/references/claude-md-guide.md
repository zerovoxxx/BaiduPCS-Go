# CLAUDE.md 写法指南

读取时机：fresh 初始化后补全入口、migrate 语义迁移，为复杂项目新增 / 调整章节，或 `spec` / `dev` / `ship` 处理入口内容回写时（读「入口回写边界」）。只改入口里一两句话不需要读。

## 写什么、不写什么

- 入口是上下文，不是强制。根 `CLAUDE.md` 每次会话完整加载，子目录里的文件在读到该目录的文件时才加载；Claude Code 不把块级 HTML 注释放进上下文，其他宿主未必。必须每次发生的行为（格式化、禁用命令、密钥检查）交给 hook、权限规则或 CI，入口里只写需要判断力的约束，或指向这些机制。
- 只写读代码读不出来、写错会出事的内容。逐条自问：模型读一遍代码能得出吗？得出就不写；目录树、依赖清单、通用语言惯例都不写。
- 每条规则可检查。“注意性能”不可检查；“列表接口必须分页，上限 100”可检查。
- 全文控制在 200 行内。细节拆到 `docs/<topic>/`，在「知识导航」里链接，不继续堆在入口。
- `架构地图`、`项目红线` 始终保留章节，没有内容时留空：标题可见、无正文，标题下保留注释作填写提示。其余没有内容的章节整节省略，不留空标题；模板里这类章节是注释，满足回写条件且有内容时再解除注释写入。

## 章节结构

标题不编号，章节之间用名称互相引用（存量项目各自的编号不同）。顺序即推荐顺序：命令与架构靠前，红线其次，指针与协议靠后。

| 章节 | 放什么 | 行数预算 |
|---|---|---|
| 项目画像 | 项目是什么、给谁用，一两句 | ≤5 |
| 命令速查 | 质量门命令表，带「何时跑」列，决定验证范围 | ≤15 |
| 架构地图 | 技术栈与工程边界（语言、框架、版本、模块划分、依赖方向）；业务子领域与边界（职责、归属目录、对外接口，关键模型关系几行加链接）。只写已定设计或可证实的实现事实，尚未实现的标明为已定设计 | ≤40 |
| 项目红线 | 绝对不能逾越的约束与不变量，一条一件事，每条以 `[禁止]` 或 `[须授权]` 开头；项目特有的不可逆操作和暂停点也写在这里 | ≤30 |
| 项目约定（特殊约定） | 开头是不属于任何领域的通用约定（模板默认两条，可增删）；再按需分节：工程联动与契约、领域实现、数据库约束 | ≤45 |
| 领域专用词汇 | 只收有歧义、或与代码命名不一致的词，一词一行 | ≤15 |
| 知识导航 | 设计文档、ADR、DDL、runbook 的链接，各配一句何时读 | ≤15 |
| AI 协作规范 | 由 Harness 维护的受管块：「开发原则」4 条加「编程哲学」小节，升级时整体替换，不手改 | 固定，约 50 行 |

## 单一来源

同一件事只在一处写成句子，用一个问题决定它归哪：

| 在说什么 | 放哪 |
|---|---|
| 有什么、怎么连（事实） | 架构地图 |
| 不许什么 | 项目红线 |
| 改了它要跟着改什么 | 项目约定的「工程联动与契约」 |

例（通用示例，不是某个项目的规则）：

| 位置 | 写法 |
|---|---|
| 架构地图 | Worker 经 Execution API 取数，依赖方向 Worker → API Server → DB |
| 项目红线 | `[禁止]` Worker 直连元数据库 |
| 工程联动与契约 | 改 Execution API 的请求 / 响应 → 同步 Task SDK 与 Worker 客户端并跑契约测试 |

一句话既像事实又像禁令时，写成禁令放进「项目红线」，架构地图只留结构事实。架构地图和「工程联动与契约」里不出现“禁止 / 不得”。

「数据库约束」只写本项目选定的方案和与默认做法的差异：金额的存储方案、租户列与审计列约定、迁移工具链与目录、被禁止的数据库操作、账务表的不可变性。命名、类型、索引、迁移实践等公共规范由 `db-design`（astack-coding，可单独安装，需确认宿主可用）承担，不在入口重复。

## 新项目补全

初始化得到的入口有画像、命令速查、留空的「架构地图」与「项目红线」、两条默认约定和受管块，其余章节在模板里是注释。除 `命令速查` 外，模板初始化与结构升级不自动授权填充项目事实与约定。

1. `命令速查`：从 `package.json` scripts、Makefile / justfile、`pyproject.toml`、tox、CI workflow 找真实可运行的命令填表；找不到的行写“不适用”，不编造命令。
2. 「架构地图」「项目红线」：章节已在模板里，没有内容时保持留空；内容按下面的「入口回写边界」补全。能由配置证实的技术栈（`engines`、`.nvmrc`、`go.mod`、`pyproject.toml` 里的版本与框架）同样按该边界处理，未获写入要求时只在报告里列为候选。
3. 其余章节（领域专用词汇、知识导航、项目约定的各小节）仍是注释，满足回写条件且有已定内容时才启用，不为填满模板而写。

## 入口回写边界

本节约束 `CLAUDE.md` 的项目内容回写，包含通过指向它的 `AGENTS.md` 入口修改同一文件；`spec`、`dev`、`ship` 引用本节，受管块只保留摘要，SPEC / PLAN 的记录维护仍按各自流程执行。

**唯一自动回写场景。** 新项目的初始架构设计定稿后、进入实施前，相关决策已按 `spec` 的决策分级确认或授权，由 `spec` 自动把已定内容按下表写入入口，无需另问一次是否写入。未定稿的设计留在 SPEC 或讨论中；该授权不延伸到骨架完成、后续开发、已有项目重建、验证或 ship。

| 已定内容 | 写到哪 | 内容边界 |
|---|---|---|
| 技术栈、模块职责、依赖方向与业务子领域边界 | `架构地图` | 尚未实现时注明为已定设计，引用 SPEC；不声称代码已按此落地 |
| 项目特有的禁止事项、不变量与须授权操作 | `项目红线` | 按 `[禁止]` / `[须授权]` 标记，每条一件事 |
| 项目特有的领域落地方式、状态与职责约定 | `项目约定` 的 `领域实现` | 只写已定约定，细节链接到 SPEC 或领域文档 |
| 项目选定的数据表示、一致性与迁移约定等 | `项目约定` 的 `数据库约束` | 只写本项目决策，不复制 `db-design` 的公共规范 |
| 其他已经确定、适合长期保留的入口内容 | 对应既有章节 | 命令必须已验证可运行；仍待骨架创建的命令不写成可执行事实 |

**其余场景按明确授权写入。** 需要同时满足“用户已明确决策”和“用户明确要求写入入口”；两者可在同一句或同一会话的不同轮次给出。按用户指定的内容与范围执行，位置未指定时按章节职责归位，已有授权不重复询问。仅说“采纳方案”“按这个做”“你定”，只解决方案或实施授权，不自动包含入口写入授权。

| 场景 | 用户尚未要求写入时 | 用户明确决策并要求写入后 |
|---|---|---|
| 现有 `架构地图` 为空或缺少当前模块 | 将相关事实整理在 SPEC / 报告，可建议补充入口 | 按确认内容补充对应章节 |
| 骨架完成，或模块划分、依赖方向、版本、接口归属变化 | 报告实际结果与回写候选 | 在授权范围内更新已定内容与实际事实 |
| 质量门命令新增或变化 | 将实际命令和验证结果记录在 SPEC / 报告 | 更新 `命令速查` 中对应的已验证命令 |
| 决策已确认，或识别出领域实现、数据库约束、项目红线候选 | 提出候选内容与依据，等待用户决定是否写入 | 将用户已定的规则写入相应位置 |

回写的约束：

- 自动或已授权回写完成后，在报告中列出依据、内容和写入位置。
- 给出回写建议时附候选文字、拟写位置和理由；未收到明确写入要求就不修改入口，其余已授权工作继续，不把回写建议变成开发或 ship 的等待闸门。
- `架构地图` 区分已定设计与实现事实，不出现“禁止 / 不得”；项目约定与红线遵守「单一来源」，不重复写同一规则。
- 遵守「章节结构」的行数预算和全文 200 行上限；细节留在对应文档，满足回写条件时才向入口添加导航链接。
- 模型仅从代码推断出的长期约束仍是候选，不直接转成项目红线、领域实现或数据库约束。
- 不写当前进度这类易变内容，不在内容回写中修改受管块。
- 只有满足本节回写条件后，才创建缺失章节或启用注释小节，按既有章节顺序放置。新项目通过 `harness-init` 初始化入口；其余场景入口不存在时，在用户明确要求写入该入口的授权范围内创建，未获写入要求只报告或建议。

**`ship` 收口。** 第 4 步只执行用户明确要求的入口回写，或报告候选建议；SPEC / PLAN 更新和已授权交付按原流程继续。变更涉及架构、接口或数据模型，不自动取得更新 `CLAUDE.md` 的权限。

## 迁移旧入口

把旧 `CLAUDE.md` / `AGENTS.md` 的内容按章节归位，不改变含义：

| 旧内容 | 归入 |
|---|---|
| 项目简介 | 项目画像 |
| 构建、测试、lint、迁移命令 | 命令速查 |
| 技术栈、模块职责、依赖方向 | 架构地图 |
| 禁止事项、不变量、需授权的操作 | 项目红线（逐条补标签） |
| 编码、错误处理、测试风格；跨层同步要求；领域流程 | 项目约定 |
| 术语表 | 领域专用词汇 |
| 文档、ADR、DDL 的链接 | 知识导航 |
| 通用的执行边界、编码原则 / 编码哲学、Spec 工作流 | 删除，由 AI 协作规范承担 |

目录树、依赖列表这类读代码就能得出的内容可以删，其余全部保留；拿不准归哪的规则放进项目约定并标“待确认”。
