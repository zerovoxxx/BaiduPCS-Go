# Dev：按请求、SPEC 或 PLAN 实现

## 核心目标

以最小范围实现明确的请求、SPEC 或 PLAN，让每条验收标准都有对应的实际改动和覆盖最终内容的新鲜验证证据；使用 SPEC / PLAN 时，状态和验证记录同步写回文档。

## 执行流程

### 1. 选择输入模式并准备

- 做什么：用户明确选择的模式优先（用户说不写 SPEC / PLAN 即直接请求模式）；未指定时按下表选择：

  | 模式 | 条件 |
  |---|---|
  | PLAN | 用户指定，或当前变更有明确的 `_PLAN.md` 执行入口 |
  | SPEC | 没有执行 PLAN，但存在匹配当前请求的 `_SPEC.md` |
  | 直接请求 | 目标清晰且没有匹配的 SPEC / PLAN，或用户明确要求直接开发 |

  - 读取：从目标文件、所属模块、引用链和相关测试开始；SPEC / PLAN 模式再读其相关章节（用 `list` 定位，不遍历历史 SPEC）；路径不明时先做一次定向搜索。
  - 确定：假设、成功标准和验证命令；输入之间冲突时按用户最新目标和适用指令定本地方案，说明重要假设并继续。
  - 状态：SPEC / PLAN 模式把 SPEC `文档状态` 设为 `开发中`（PLAN 保持 `待执行`），并更新 `最后更新`。
- 产出：明确的范围、成功标准和验证命令；SPEC 状态为 `开发中`（如适用）。

### 2. 实现

- 做什么：做满足目标的最小改动，沿用项目已有模式，不顺手重构无关代码。缺陷修复和高风险的计算、策略、数据转换，先写能复现问题的测试再实现；已有测试足以覆盖的小改动直接改并跑聚焦测试；文档、配置和纯脚手架不为形式新增测试。跨层契约同时改生产方与消费方。PLAN 模式按任务顺序执行，每个任务验证后更新勾选。需要专业核对时可复用对应专项 skill（如用 `db-design` 核对 migration 是否符合已定方案），仅核对已定方案不增加审批步骤；核对结果要求改变已确认的数据模型或业务决策时，按“方案边界”处理。
- 产出：改动与必要的测试。

### 3. 验证

- 做什么：运行覆盖最终文件状态的验证。
  - 命令按优先级确定：① 用户明确要求的命令，以及 PLAN / SPEC 已写明的具体命令（都适用且不冲突时都执行）；② 项目 `CLAUDE.md` 的“命令速查”（旧版为“项目质量门”）；③ 仓库已有 wrapper、package script、构建清单或 CI 入口中无歧义的命令；④ 仍无入口时执行可行的检查并报告验证缺口，不编造命令或通过结果。
  - 失败时记录失败命令，自行定位、修复并重跑受影响检查。
  - 实现中需要改变验证命令时，SPEC 模式先更新 SPEC，直接请求模式在报告中说明原因与新命令。
  - 格式化或自动修复只作用于本次范围，产生文件改动后检查 diff 并重新验证。
- 产出：每条命令的 PASS / FAIL 证据。

### 4. 验收核对

- 做什么：把每条验收标准（或直接请求的成功标准）映射到实际改动和验证证据。“用户能看到 / 能用”必须在呈现层验证渲染值、状态或交互结果，API、数据层或单元测试只证明底层契约（口径见 `spec` 的 [references/acceptance.md](../spec/references/acceptance.md)）；跨层契约同时核对生产方与消费方，并运行能发现接口漂移的质量门。通读本次 diff，确认只含本次范围内的改动、没有调试残留。
- 产出：验收映射结论；有缺口则回到步骤 2。

### 5. 记录与收口

- 做什么：
  - **SPEC / PLAN 模式**：在 SPEC `验证记录` 追加行，按下方规则更新状态，刷新 `最后更新`（ID 与文件名不变），再运行同级 spec skill 的 `python3 scripts/spec_workflow.py list --root <项目根目录>` 校验元数据。实现与旧 SPEC / PLAN 不一致时，按当前用户目标同步文档并说明原因，不为范围内的可恢复调整重复请求批准。
  - **直接请求模式**：不创建 SPEC / PLAN；在最终报告中写明实际命令、PASS / FAIL、覆盖范围和关键假设。
  - **入口回写**：遵循 [claude-md-guide.md](../harness-init/references/claude-md-guide.md) 的「入口回写边界」，只执行用户已明确决策并要求写入的入口更新；其余候选内容只在报告中建议，不把回写作为开发完成条件。
  - **交接**：结束时交接本次改动范围、验证证据和下一阶段；本次交付需要独立 Review（条件见 `spec` 的验证计划）时指向现有 `open-code-review-delegate`，由 `dev` 结束后的独立阶段执行。

  验证记录行格式：

  ```markdown
  | YYYY-MM-DD | `实际命令` | PASS / FAIL | 覆盖范围或失败原因 |
  ```

  状态规则：PLAN 全部任务验证 PASS → PLAN `已完成`；本次授权的交付目标已满足 → SPEC `已完成`；另有已授权的提交 / 推送，或本次交付所需的独立 Review 等阶段尚未完成时保持 `开发中`，由后续阶段按现有状态规则收口（dev 不强制调用 ship），不新增状态词；外部依赖或缺失事实使任务确实无法推进 → SPEC `阻塞` 并写明原因，PLAN 保持原状态，继续可独立推进的任务。
- 产出：SPEC / PLAN 更新，或最终报告；阶段交接。

## 产出要求

> 完成时可逐条核对的交付物与验收门；做事方式写在执行流程里。

- 改动只含本次范围：`git diff` 中没有无关重构、无关格式化和调试残留。
- 每条验收标准（或直接请求的成功标准）都有对应改动，以及覆盖最终文件状态的同层级验证证据（命令 → PASS）。
- 缺陷修复和高风险逻辑有先失败后通过的复现测试，或在报告中说明已有测试已覆盖。
- [SPEC / PLAN 模式] SPEC `验证记录` 已追加行，状态与 `最后更新` 已更新，PLAN 勾选已更新；`list` 无报错。
- [用户明确要求回写] 报告列出已写入的内容与位置；[存在回写候选但未授权] 只列建议。
- 最终报告：实际执行的命令及 PASS / FAIL、覆盖范围、关键假设、本次改动范围与下一阶段，以及未完成的检查或验证缺口。

## 特殊说明

> 跨步骤的策略与边界，每条带理由；只在单个步骤用到的规则写在该步骤里。

- **执行边界**：只读检索、本地草稿、可恢复的修改和常规本地检查直接推进；命名、实现细节和验证命令从代码与配置推断，关键假设写进产出；缺失的业务事实可一次性询问，同时继续不依赖答案的工作；会话中已给出的授权持续有效，已获授权的动作不重复确认，未获答复不等于授权。可恢复的事做错了可以重来，不可逆的事做错了无法挽回，所以只在“不可逆或难以恢复、且尚未获得授权”的动作前暂停：不执行该动作，其余工作照常，备好 diff / dry-run 与回退说明，并在报告中请求授权。本 skill 的暂停点：删除持久数据、丢弃无法恢复的未提交改动、改写已发布历史、破坏性迁移、对生产 / 外部系统的写入。
- **测试完整性**：不通过删除、弱化或跳过测试 / 断言让检查变绿；只有原断言本身错误时才修改，并在报告中说明——被削弱的测试即使通过，也不再是证据。
- **证据复用**：相同文件状态、依赖和基线的有效验证证据可复用，相关内容变化后才重验；不基于意图、视觉检查或旧测试输出声明完成——重复验证同一内容没有新信息，而“完成”必须有覆盖最终内容的证据。
- **方案边界**：`dev` 只实施，不判定工作类型，也不自行改方案。实施中发现 SPEC 不成立、小问题其实需要排查，或要改变用户已定的方向时，停下相关改动，说明证据和建议，回到 `spec` 更新方案，不依赖这项判断的工作继续；用户已明确“直接修”“不写 SPEC”时不自行回 `spec`，由用户选择转 `spec` 或继续直修，继续直修则按直接请求模式完成，报告写明证据和未经诊断的假设——方案和实施混在一起，改了什么就无从追溯。

## 依赖脚本

| 脚本 | 用途 | 调用 |
|---|---|---|
| 同级 `spec` skill 的 `scripts/spec_workflow.py` | SPEC / PLAN 模式更新状态后校验元数据 | `python3 "<spec-skill-dir>/scripts/spec_workflow.py" list --root <项目根目录>`；Python 3.9+ |
| 项目的质量门命令 | 实际验证（来自 SPEC / PLAN、`CLAUDE.md`、package script 或 CI 入口） | 不属于本 skill 的脚本，按步骤 3 的优先级解析 |
