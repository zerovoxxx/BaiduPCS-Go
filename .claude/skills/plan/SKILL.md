# Plan：SPEC 转实现计划

## 核心目标

把过大或风险较高、无法直接执行的 SPEC 拆成小粒度、可独立验证的任务：每个任务有具体步骤、验证命令和预期信号，每条验收标准都能追溯到任务、实现位置和验证证据。

## 执行流程

### 1. 读取输入

- 做什么：读来源 SPEC 的目标、边界、验收标准和本次实施相关的章节，SPEC 引用的现有源文件，以及影响当前任务的前置 SPEC 章节（用 `list` 定位，不递归通读历史文档）。项目入口（`CLAUDE.md` / `AGENTS.md`）已由宿主加载，无需重读。实质改变目标的未决事实标注 `Spec 待明确`，其余实现细节按项目惯例推断并记录，不把假设写成事实。
- 产出：对范围、验收和现有代码的理解。

### 2. 创建 PLAN 文件

- 做什么：新建 `docs/astack/plan/<ID>_<Slug>_PLAN.md`，沿用来源 SPEC 的 ID 与 Slug（不生成新 ID），开头放与 SPEC 一致的文档信息表：

  ```markdown
  # <标题，沿用来源 SPEC>

  > **文档信息**
  >
  > | 字段 | 值 |
  > |---|---|
  > | 文档类型 | PLAN |
  > | 需求 ID | 与来源 SPEC 相同 |
  > | 文档状态 | 待执行 |
  > | 发布版本 | 沿用来源 SPEC，未定写 `未定` |
  > | 创建日期 | YYYY-MM-DD |
  > | 最后更新 | YYYY-MM-DD |
  > | 作者 | `git config user.name` 的结果，为空写 `AI` |
  > | 关联文档 | [<ID>_<Slug>_SPEC.md](../version/<ID>_<Slug>_SPEC.md) |
  > | 一句话目标 | 一句话写出本计划要拆解和验证的交付结果 |
  ```

  PLAN 只用 `待执行` / `已完成`：新建为 `待执行`，所有任务验证 PASS 后由 `dev` 改为 `已完成`。
- 产出：PLAN 文件（含信息表）。

### 3. 拆解任务

- 做什么：按下方骨架填写正文。每个任务保持足够小，可独立验证；任务用语义锚点（函数名、章节名）定位，不用易失效的行号；验证命令按优先级确定：① 来源 SPEC 已确认的命令；② 项目 `CLAUDE.md` 的“命令速查”（旧版为“项目质量门”）；③ 仓库已有 wrapper、package script、构建清单或 CI 入口中无歧义的命令。文档类任务可用机械信号验证：`git diff --check` → 退出码 0、针对性搜索过期标记并预期零命中。

  ```markdown
  ## 文件地图与验收追溯

  | 文件 | 操作 | 职责 |
  |---|---|---|
  | `path/to/file` | 新增 / 修改 / 删除 | … |

  | 验收标准 | 任务 | 实现位置 | 验证证据 |
  |---|---|---|---|

  ## 有序任务

  ### T1 <动作 + 语义锚点>

  - [ ] 步骤 1：…
  - [ ] 步骤 2：…
  - 验证：`<可执行命令>` → <预期信号：退出码 / 测试数量 / 零命中>
  - 评审节点（跨文件契约时）：生产方与消费方一并核对

  ## 最终检查

  - [ ] 全部任务验证 PASS
  - [ ] 来源 SPEC 的 `验证记录` 已追加证据，状态已更新（由 dev 完成）
  ```

- 产出：PLAN 正文。

### 4. 校验与衔接

- 做什么：运行同级 spec skill 的 `python3 scripts/spec_workflow.py list --root <项目根目录>` 校验。用户仅要求计划时，交付 `_PLAN.md` 即完成；已要求实施时，直接进入 dev，不要求新一轮审批或显式 `/dev`。
- 产出：校验结果、交付报告。

## 产出要求

> 完成时可逐条核对的交付物与验收门；做事方式写在执行流程里。

- 文件 `docs/astack/plan/<ID>_<Slug>_PLAN.md`，ID / Slug 与来源 SPEC 相同，信息表按步骤 2 的模板填写。
- 步骤 4 的 `list` 无报错，且该需求一行同时列出 SPEC 与 PLAN。
- 每个任务至少有一条可执行的验证命令和明确的预期信号（退出码、测试数量或零命中）；没有 `<module>`、`{test}` 之类的占位符，也没有“构建通过”这类缺少命令名的检查。
- 追溯表覆盖每条验收标准：对应任务、实现位置和验证证据齐全。
- 用户可见验收项在呈现层有证据：除产出数据或 API 的任务外，还有消费端实现任务，以及对实际渲染值、状态或交互结果的断言（口径见 `spec` 的 [references/acceptance.md](../spec/references/acceptance.md)）；跨层能力的文件地图和评审节点同时覆盖生产方与消费方。
- 无法解析验证命令的步骤标注“验证缺口”，其余任务照常拆解，不因单个缺口阻塞整个计划。
- 交付报告：未决项（`Spec 待明确`）和验证缺口。

## 特殊说明

> 跨步骤的策略与边界，每条带理由；只在单个步骤用到的规则写在该步骤里。

- **执行边界**：只读检索、本地草稿、可恢复的修改和常规本地检查直接推进；命名、实现细节和验证命令从代码与配置推断，关键假设写进产出；缺失的业务事实可一次性询问，同时继续不依赖答案的工作；会话中已给出的授权持续有效，已获授权的动作不重复确认，未获答复不等于授权。可恢复的事做错了可以重来，不可逆的事做错了无法挽回，所以只在“不可逆或难以恢复、且尚未获得授权”的动作前暂停：不执行该动作，其余工作照常，备好 diff / dry-run 与回退说明，并在报告中请求授权。本 skill 的暂停点：无（只写本地文档）。
