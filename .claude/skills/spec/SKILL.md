# Spec：判定工作类型并产出方案

## 核心目标

把一次变更的目标、边界、设计、验收和验证计划写进单一 SPEC，作为后续 plan / dev / ship 的唯一事实来源：读的人不必再追问用户就能实施，并能用命令验证结果。`spec` 是产品变更的工作类型与方案入口：判定新项目、新功能、缺陷或重构并产出对应方案，`dev` 只负责按方案实施。

## 执行流程

### 1. 判定工作类型

- 做什么：工作类型以用户明确指令为准；未说明时按项目现状推断并说明依据，推断不出时询问，不猜测。
  - 范围：只路由需要整体方案或实施的产品变更。独立专项任务（用户只要求数据库设计、原型、图解、依赖检查或代码审查）直接使用对应专项 skill 交付结果，不写 SPEC，也不扩展到开发、变更执行、修复、提交或推送；已有 SPEC 就引用其相关约束，没有也不为独立任务补建。提到某个 skill 不自动缩减或扩大请求范围。
  - 小改动与小问题：小改动指目标和改法都清楚，且不涉及难以回退的决策；小问题指不用排查就知道哪错了、怎么改，且四条同时满足——现象直接指向具体位置（不用看日志或分析复现）、改法只有一种、不碰鉴权 / 金额 / 持久数据 / 对外接口、不是修过又复发的问题。二者说明判断后直接实施，不写 SPEC；有一条不满足就是需要排查的缺陷。例：按钮文案错别字、配置项名字写错、漏了 import 是小问题；偶发报错、金额有时不对、修过又复发、分不清前端还是后端、修复要改接口是需要排查的缺陷。
  - 类型判定：其余产品变更按用户明确指令 > 项目证据 > 询问的优先级定类型，“跳过调研”“不写 SPEC”“直接修”“你定”同样优先。按下表推断时用一句话说明依据后继续，不等确认；推断不出时问一句，同时继续只读调查（如“这个页面太慢”可能是缺陷，也可能是优化）。

    | 推断为 | 依据 |
    |---|---|
    | 新项目 | 仓库没有业务代码和依赖清单 |
    | 缺陷 | 已有行为不符合预期：报错、日志、失败测试、“之前可以” |
    | 重构 | 目标写明行为不变，只调整结构或依赖 |
    | 新功能 | 已有项目上新增或改变行为，作为默认 |

  - 边界情况：用户明确说“直接修”“不写 SPEC”，走 `dev` 的直接请求模式；其中发现修完现象还在、牵扯别的模块或其实需要排查时，不自行转缺陷流程，也不展开诊断，说明证据，由用户选择转 `spec` 或继续直修；没有这类明确指令而按小问题开始改，发现同样情况时停下转缺陷流程；证据和用户指令不一致时不自行改道，说明证据和建议，由用户决定；在已有代码上重建只有用户明确说才走，推断不会得出这个结论，删除旧代码属于暂停点。
  - 读对应 reference：定下类型后按下表读取；新项目缺 `CLAUDE.md` 或 `docs/astack/version/` 时先按 `harness-init` 初始化。

    | 类型 | reference |
    |---|---|
    | 新项目 | [references/new-project.md](references/new-project.md) |
    | 新功能 | [references/feature.md](references/feature.md) |
    | 缺陷 | [references/bugfix.md](references/bugfix.md) |
    | 重构 | [references/refactor.md](references/refactor.md) |
- 产出：工作类型、依据与去向。

### 2. 定位上下文与分析

- 做什么：运行 `python3 "<spec-skill-dir>/scripts/spec_workflow.py" list --root <项目根目录>`（`--active` 只列待实施 / 开发中 / 阻塞，`--all` 含归档），判断是更新已有需求还是新建；只读匹配 SPEC 的相关章节和要改的代码。项目入口（`CLAUDE.md` / `AGENTS.md`）已由宿主加载，无需重读。`list` 报旧格式（`Iteration<N>` 命名）时，先用 `harness-init` 的升级脚本迁移。再按所属类型 reference 完成分析；缺陷判定不是缺陷时，按 `bugfix.md` 的分流表报告后结束，不进入后续步骤。
- 产出：确定新建或更新哪份 SPEC；分析结论。

### 3. 分配 ID（仅新需求）

- 做什么：运行 `python3 "<spec-skill-dir>/scripts/spec_workflow.py" id --root <项目根目录>`，得到 `YYMMDD-xxx`（UTC 日期 + 三位随机小写字母或数字，如 `261029-a7f`）；生成器已避开当前工作区、归档及同仓库其他 worktree 的已用 ID。更新既有需求沿用原 ID（包括旧的 `YYMMDDHHmm-xxx`），不按分支或合并顺序重编号。文件放在 `docs/astack/version/`，命名为 `<ID>_<PascalSlug>_SPEC.md`，`PascalSlug` 为英文 PascalCase。
- 产出：SPEC 文件名。

### 4. 起草或更新 SPEC

- 做什么：按下方「SPEC 格式与内容要求」写，类型 reference 给出对应类型的写法（缺陷 SPEC 用精简写法，七个必填章节仍齐全）。
  - 非目标、呈现位置、命名和实现方案从用户目标与相关代码推断，重要假设写进 SPEC 后继续；确需用户补充的业务事实标注“待明确”，不编造。
  - 更新既有 SPEC 时就地编辑，保留已有的验证记录和变更日志，并刷新 `最后更新`。
  - 涉及复杂方案设计（多模块 / 长期维护的新结构 / 持久数据或兼容契约 / 多个有明显取舍的方案）或难以回退的决策时，先读 [references/design-tradeoffs.md](references/design-tradeoffs.md)，按决策分级处理，补充 `外部参照与设计取舍` 章节和决策记录。
- 产出：SPEC 文件。

### 5. 校验

- 做什么：在项目根目录运行 `bash "<spec-skill-dir>/scripts/spec-lint.sh" "docs/astack/version/<ID>_<PascalSlug>_SPEC.md"`（monorepo 子项目追加 `--root <项目根目录>`）。ERROR 与本次内容产生的 WARN 必须修正并重跑；既有 WARN 在报告中说明即可。报重复 ID（并行分支的 ID 碰撞）时，保留已进入目标分支的 ID，为新建需求重新生成并修正其引用，不能覆盖另一需求（细则见 `ship` 的 `references/merge-conflicts.md`）。
- 产出：校验结果。

### 6. 衔接

- 做什么：用户只要求 SPEC 时，交付文档即完成；已要求实现整个目标时，直接进入 dev（SPEC 过大或风险较高才先 plan），不等待新的 slash 调用。有未确认的难以回退决策时，把决策清单集中交给用户，确认后再进入 dev。入口内容回写遵循 [claude-md-guide.md](../harness-init/references/claude-md-guide.md) 的「入口回写边界」：新项目在架构设计定稿（决策已确认或授权）后、进入实施前写入已定内容；其余场景只记录用户明确要求写入的已定内容，或在报告中提出候选建议，不因入口空缺或方案获确认而默认写入。
- 产出：交付报告。

### SPEC 格式与内容要求

**文档信息表**：位于一级标题之后、第一个二级标题之前，是需求 ID、状态、发布版本和日期的唯一来源；PLAN 使用同一张表。发布版本未定写 `未定`，多个需求可共用同一版本。

```markdown
# <标题>

> **文档信息**
>
> | 字段 | 值 |
> |---|---|
> | 文档类型 | SPEC |
> | 需求 ID | 与文件名一致的 ID |
> | 文档状态 | 待实施 |
> | 发布版本 | 未定 |
> | 创建日期 | YYYY-MM-DD |
> | 最后更新 | YYYY-MM-DD |
> | 作者 | `git config user.name` 的结果，为空写 `AI` |
> | 关联文档 | 无 / 前置 SPEC 链接 / 需求来源 |
> | 一句话目标 | 一句话写出本需求要达成的可验证结果 |
```

**状态**：全流程只用下列词；标准流转 `待实施 → 开发中 → 已完成`，`阻塞` 可从任意状态进入，解除后回到原状态。PLAN 只用 `待执行`、`已完成`。

| 状态 | 含义 | 主要写入者 |
|---|---|---|
| `待实施` | 目标、边界、验收和验证计划已写清，可进入 plan 或 dev | spec |
| `开发中` | 已开始按 SPEC / PLAN 修改代码或文档，尚未完成最终交付 | dev |
| `已完成` | 验证、SPEC 更新及本次请求的交付终点已完成（不强制包含提交或推送） | dev / ship |
| `阻塞` | 缺少必要信息、外部依赖不可用或连续验证无法推进 | 任一流程 |

**章节**：以下名称必填，顺序建议如下（编号可选）；较大变更可补充方案对比、详细设计、风险与回退。

| 章节 | 内容要求 |
|---|---|
| 目标与非目标 | 要达成的可验证结果、明确不做什么，以及据以推断的假设 |
| 变更范围 | 涉及的文件 / 模块 / 接口及各自职责（新增、修改、删除）；用户可见能力写明实现位置 |
| 实现说明 | 方案要点、关键设计决定、数据流或契约变化；复杂方案另加 `外部参照与设计取舍`（简记外部参照、可借鉴点、不采用点和本次取舍） |
| 验收标准 | 逐条可判定（输入 → 可观察结果）；用户可见项写明用户在哪里做什么、看到什么值或状态 |
| 验证计划 | 真实存在、适用于本次影响面的命令 + 预期信号（规则见下） |
| 验证记录 | 表格，列为日期、命令、结果、备注；spec 阶段写“待执行”，由 dev / ship 追加行 |
| 变更日志 | 日期 + 变更摘要；每次更新 SPEC 都追加 |

**验证计划**：每个 SPEC 至少一条可执行命令。命令按优先级确定：① 当前任务匹配的 SPEC / PLAN 中已有的具体命令；② 项目 `CLAUDE.md` 的“命令速查”（旧版为“项目质量门”）；③ 仓库已有 wrapper、package script、构建清单或 CI 入口中无歧义的命令；④ 仍无入口时完成可行的静态检查并记录验证缺口。只写本仓库真实存在的命令，模块、测试目标和路径写具体，不借用其他技术生态的默认工具。最低要求：

| 变更类型 | 最低验证 |
|---|---|
| Markdown / 文档 / skill | `git diff --check` + 针对性搜索过期引用；项目有更严格门槛时同时执行 |
| 业务逻辑 / 数据转换 | 项目定义的聚焦测试；缺陷修复或高风险逻辑优先加能复现问题的回归测试 |
| API / Schema / 跨边界契约 | 聚焦契约或集成测试 + 项目定义的编译、类型检查或构建门 |
| 基础设施 / DB | 项目定义的 repository / migration 验证 + 适用的完整质量门 |
| 用户可见行为 | 在实际呈现层断言渲染值、状态或交互结果 + 适用的质量门命令 |

“人工检查”不能作为唯一验证方式，除非变更纯属视觉呈现且记录了截图或手动步骤。声明用户能看到 / 操作某流程的验收项，按 [references/acceptance.md](references/acceptance.md) 的口径写。

新项目 SPEC 可以写由骨架任务创建的命令，标注“骨架任务创建”，骨架完成时必须能跑通。每份 SPEC 还要写明是否需要独立 Review 及理由：它在 `dev` 完成后、`ship` 前由主流程复用现有 `open-code-review-delegate` 执行，评审规则沿用对应 skill，不并入 `dev`。满足任一条件就需要：

- 用户明确要求。
- 跨模块或跨层改动。
- 改持久数据、迁移、对外接口或兼容契约。
- 涉及鉴权、密钥、权限、金额等高风险逻辑。
- 根因不明显的缺陷，或缺陷修复改动超过 5 个文件。
- 新项目的交付，或大范围重构。

用户明确说不评审则跳过，明确要求评审则执行；未明确要求时按上述条件判断：命中任一条件即需要，未命中则不跑（小改动、小问题、纯文档通常不命中）。SPEC 没写或直接请求模式时，主流程在 `dev` 结束后引用同一条件判断，不为此补建 SPEC。

评审上下文包含用户目标、相关验收标准、架构事实与项目红线，范围对应本次改动；命令、依赖准备、发现分类、修复授权和失败处理都遵循被调用的 skill。主流程把实际评审命令、结论、覆盖范围和未决项写回 SPEC 的 `验证记录`（直接请求模式写进报告）；跳过或未完成时写明原因，不以 `dev` 自查代替独立评审结论，所需 Review 尚未完成时不报告完整交付已完成。需要修复时按评审 skill 和本次授权处理，交给 `dev` 的修复作为新的实施阶段，完成后重跑受影响检查；改变 SPEC 已定方向时先回到 `spec`。评审结论和必要修复的验证证据就绪后，才衔接本次已授权的 `ship`；未请求 ship 时交付评审结果即可。

## 产出要求

> 完成时可逐条核对的交付物与验收门；做事方式写在执行流程里。

- [写 SPEC 时] 文件 `docs/astack/version/<ID>_<PascalSlug>_SPEC.md`；更新既有 SPEC 时 `最后更新` 已刷新。
- [写 SPEC 时] `spec-lint.sh` → `Spec Lint PASS`，无 ERROR（它检查文件名与 ID 一致、信息表九个字段、状态词、日期和 PLAN 来源），本次内容产生的 WARN（如缺少核心章节）已清零。
- [写 SPEC 时] 七个必填章节齐全且满足「SPEC 格式与内容要求」：验证计划至少一条真实可执行的命令，每条验收标准可判定，用户可见项有呈现层的证据。
- [写 SPEC 时] 假设与未决项写在 SPEC 里（目标与非目标 / 验收标准 / 外部参照与设计取舍），不只留在对话中。
- [不写 SPEC 时] 报告写明判定结果、证据和去向。
- [有难以回退的决策] 决策记录写明结论和确认方式，未确认项列在交付报告。
- [写 SPEC 时] 交付报告：SPEC 路径、关键假设、未决项、校验结果。

## 特殊说明

> 跨步骤的策略与边界，每条带理由；只在单个步骤用到的规则写在该步骤里。

- **执行边界**：只读检索、本地草稿、可恢复的修改和常规本地检查直接推进；命名、实现细节和验证命令从代码与配置推断，关键假设写进产出；缺失的业务事实可一次性询问，同时继续不依赖答案的工作；会话中已给出的授权持续有效，已获授权的动作不重复确认，未获答复不等于授权。可恢复的事做错了可以重来，不可逆的事做错了无法挽回，所以只在“不可逆或难以恢复、且尚未获得授权”的动作前暂停：不执行该动作，其余工作照常，备好 diff / dry-run 与回退说明，并在报告中请求授权。本 skill 的暂停点：难以回退的决策未经用户确认时，不进入 dev。
- **专项 skill**：`db-design`、`huashu-design`、`archify`、`py-dep-upgrade`、`open-code-review-delegate` 按任务需要自动选用，用户指定或排除优先，不逐项询问；采用必要的专业方法，额外产物按需生成，普通页面能沿用现有组件时不默认追加原型或图解。工作类型和阶段不决定是否调用，任务和所需产物才决定，执行方法与运行依赖由各 skill 自己维护——选择不绑定类型或阶段，一次专业核对才不会被扩大成完整流程。

## 依赖脚本

脚本要求 Python 3.9+，不依赖第三方包；ID 日期支持 2000–2099 年。

| 脚本 | 用途 | 调用 |
|---|---|---|
| `scripts/spec_workflow.py` | 生成 ID、按需列出需求、校验文档（canonical 实现；`harness-init` 与 `ship` 内置逐字节相同的副本） | `id --root <项目根目录>`；`list --root <项目根目录> [--active] [--all]`；`lint [<SPEC 路径>] [--root <项目根目录>]` |
| `scripts/spec-lint.sh` | `spec_workflow.py lint` 的包装 | `bash … <SPEC 路径> [--root <项目根目录>]` |
