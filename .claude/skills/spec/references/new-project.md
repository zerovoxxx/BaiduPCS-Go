# 新项目方案

读取时机：`spec` 第 1 步判定为新项目（仓库没有业务代码和依赖清单，或用户明确指定）后。按项目规模取舍，不适用的项写一句原因后跳过。决策确认与调研遵循 [design-tradeoffs.md](design-tradeoffs.md)，入口回写遵循 [claude-md-guide.md](../../harness-init/references/claude-md-guide.md) 的「入口回写边界」。

## 方案步骤

1. 需求：解决什么问题、给谁用、怎样算成功。
2. 约束：规模、预算、部署环境、合规、谁来维护。
3. MVP：第一版做到哪，明确不做什么。
4. 行业调研：按 `design-tradeoffs.md` 的调研规则，新项目必做。
5. 选型与架构：默认用成熟技术，敲定分层、模块边界、依赖方向和目录结构；图解能帮助解释复杂关系或用户要求图示时，使用 `archify`。
6. 交互：写明用户流程、界面状态或 CLI / API 样例；需要原型探索或视觉评审时使用 `huashu-design`，可直接明确的交互沿用现有组件或用文字说明。
7. 数据与接口：涉及实质性关系型数据建模、表结构、索引或迁移设计时，使用 `db-design`；接口契约写进 SPEC。
8. 横切设计：鉴权、配置与密钥、日志、错误处理、部署、测试策略。
9. 风险验证：拿不准能不能做的，先做一次性验证，代码不保留。
10. 决策确认与入口补全：第 5 到 8 步的决策按决策分级集中确认一轮；设计定稿后、进入实施前，按「入口回写边界」写入已定架构、项目红线、领域实现和数据库约束等内容。

交互放在库表接口之前，因为页面流程决定接口和数据。专项 skill 按任务需要选用，用户指定或排除优先，不绑定工作类型或阶段。

## 必含验收标准

新项目 SPEC 必须包含以下三条验收标准；第 3 条在架构设计阶段由 `spec` 完成，`dev` 沿用已定内容实施，骨架完成后新增的入口内容按「入口回写边界」取得明确写入授权：

1. 写明运行命令，能跑通一条最小的端到端链路，骨架是第一个任务。
2. 运行与验证命令写明并验证；`命令速查` 只含已验证的命令，骨架完成后新增命令先记录在 SPEC / 验证报告，需要更新入口时按「入口回写边界」取得明确写入授权。
3. 架构设计定稿后，`架构地图`、`项目红线`，以及适用的 `领域实现`、`数据库约束` 已按职责写入入口；尚未落地的结构标明为已定设计，不把草案或推断写成现有实现。

## 重建分支

用户明确要求在已有代码上重建时，同样走本流程，另外列出要保留的行为、数据、接口和迁移方式；使用本 reference 不等于获得入口回写授权，已有项目仍按「入口回写边界」的明确授权规则处理。
