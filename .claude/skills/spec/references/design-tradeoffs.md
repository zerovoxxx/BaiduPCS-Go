# 复杂方案设计：决策分级、外部参照与设计取舍

读取时机：SPEC 涉及复杂方案设计，或类型 reference 要求按决策分级确认、按调研规则调研时。局部修正，或已有方案足以支撑判断时不需要，也不为省略调研补形式化说明。

## 何为复杂方案设计

满足任一项即是：

- 显著影响多个模块、用户流程或长期维护方式。
- 引入需要长期维护的新结构、抽象、依赖或约定。
- 改变持久数据或对外兼容契约，存在实质迁移风险。
- 存在多个可行方案，且在复杂度、兼容性、扩展性、性能、可靠性或用户体验上有明显取舍。

## 做法

1. 先理解本仓库的现有实现、约束和相关历史 SPEC（用 `list` 定位，只读相关章节），不用外部方案覆盖本项目事实。
2. 参考相同问题域的成熟做法、主流项目、官方文档或通用工程实践；是否调研按下面的「调研规则」，信息可能过期，或用户明确要求行业调研时，先联网确认。
3. 在 SPEC 中加入 `外部参照与设计取舍` 章节，简短记录：外部参照、可借鉴点、不采用点、本次取舍；难以回退的决策按下面的「决策分级」确认并写入决策记录。
4. 外部参照必须落到设计边界、方案选择、验收标准或验证计划上，不把“行业最佳实践”当口号。

## 决策分级

| 级别 | 例子 | 处理 |
|---|---|---|
| 可回退的细节 | 命名、内部函数、测试组织 | 自己定，写进 SPEC 或报告 |
| 难以回退或取舍明显 | 技术栈、架构边界、持久数据、对外契约、核心交互、重依赖 | 给推荐，一轮集中确认 |
| 要改用户已定的方向 | 改范围、改类型、换用户指定的技术 | 列出原方向、建议、理由和判断错的代价，批准才变 |

- **决策清单**：至少给“最小可行”和“长期最优”两个方案，写明复用什么、风险、推荐和理由。
- **一轮集中**：一次列出当前能回答的决策，只有新决策出现时才开下一轮。
- **用户说“你定”**：第二级采用推荐方案并记为用户授权。第三级不适用，方向变更必须有明确批准。
- **未确认时**：停在 SPEC，状态保持 `待实施`，不进 `dev`。未获答复不等于授权。

决策记录写在 SPEC 的 `外部参照与设计取舍` 章节，确认方式只用 `用户确认`、`用户授权`、`待确认`：

```markdown
| 决策 | 方案与推荐 | 结论 | 确认方式 |
|---|---|---|---|
| 存储选型 | A 最小可行 / B 长期最优；推荐 A | A | 用户确认 |
```

## 调研规则

- 新项目必做。新功能只在有难以回退的决策或用户要求时做。缺陷只在错误陌生或假设连续落空时做。
- 结果分三层：行业共识、近期做法（要质疑）、结合本项目的判断。
- 搜索只用通用类目词，不带产品名和内部信息；搜错误信息前去掉主机名、路径、SQL 片段和客户标识。
