# 缺陷诊断与缺陷 SPEC

读取时机：`spec` 第 1 步判定为缺陷或需要排查的小问题后。诊断在 `spec` 完成，不改产品代码：复现用工作区外的临时脚本，确需临时插桩时结束前还原。决策分级与调研规则见 [design-tradeoffs.md](design-tradeoffs.md)。

## 诊断步骤

1. 定严重度：线上事故先给止血方案（回滚、关开关），用户授权后执行，再查根因。
2. 收集证据：报错、日志、用户描述、最近改动。
3. 复现并判定，按下表分流。
4. 定位根因：提假设再验证，没查到根因不出修复方案。连续 3 个假设不成立就停下，报告已排除的方向，由用户选择继续、升级或加日志等下次。错误陌生或假设连续落空时才按调研规则查外部资料，搜索前先脱敏。
5. 设计修复：写明当前行为、期望行为、不能变的行为；遵守现有架构；排查同类问题；判断已写错的数据要不要修。修复要改超过 5 个文件，或涉及难以回退的决策时，按决策分级确认。
6. 写缺陷 SPEC。

| 判定 | 去向 |
|---|---|
| 确认缺陷 | 写缺陷 SPEC，用户要求修复时进入 `dev` |
| 其实是需求问题 | 不写缺陷 SPEC，给出证据，由用户决定是否转新功能 |
| 环境或使用问题 | 不写 SPEC，给出证据和处理建议 |
| 无法复现 | 不写 SPEC，报告已查证据，由用户选择继续、加日志或放下 |

涉及表结构、索引或 migration 的缺陷，按任务需要使用 `db-design` 的专业规则核对，用户指定或排除优先，不绑定工作类型或阶段。

## 缺陷 SPEC 写法

缺陷 SPEC 是精简写法，七个必填章节都保留，所以 lint 和 `spec_workflow.py` 不用改：

| 章节 | 写什么 |
|---|---|
| 目标与非目标 | 当前行为、期望行为、不能变的行为 |
| 变更范围 | 受影响文件、同类排查结果、已写错数据的处理 |
| 实现说明 | 严重度、判定证据、根因、修复方案；能变成 lint 或测试的防复发规则 |
| 验收标准 | 原场景不再复现、不能变的行为保持、回归测试先失败后通过 |
| 验证计划 | 回归测试命令、受影响的质量门、是否需要独立评审 |
| 验证记录 | 待执行 |
| 变更日志 | 创建记录 |

`dev` 按缺陷 SPEC 实施时不重新诊断，沿用其第 2 步现有规则：先写能复现问题的测试，再实现。
