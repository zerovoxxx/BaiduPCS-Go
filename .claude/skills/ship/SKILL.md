# Ship：验证并交付

## 核心目标

在用户授权的交付终点内，用覆盖最终内容的新鲜验证、规范的提交信息和安全的 git 操作交付当前变更。授权多少做多少：只要求最终验证就不提交，只要求提交就不推送；用户明确要求或仓库工作流规定时，才推送或创建 PR / MR。

## 执行流程

授权终点决定执行哪些步骤：仅验证 → 1、3、4；提交 → 再加 5；推送或 PR / MR → 再加 2、6（步骤 2 在步骤 3 之前执行）。

### 1. 预检

- 做什么：运行 `git status --short --branch`，确认变更、分支、进行中的操作和交付目标。
  - 无未提交变更且无未推送提交 → 报告无变更并结束，无需询问；工作区干净但有本地提交待推送，是合法的输入。
  - 正在 merge / rebase / cherry-pick 且请求未包含继续该操作，或处于 detached HEAD、无法确认当前分支 → 不做提交、对齐和远端动作，也不擅自中止用户已有的操作；继续可行的只读检查与本地验证，并报告原因。
  - 含远端交付时确定目标：有上游跟踪则用其远端分支；否则用用户指定或仓库约定的目标；仍没有且仓库只有一个 remote，则推送到该 remote 的同名分支并设置上游；有多个 remote 又没有任何依据时，完成本地交付并一次性询问目标，不猜测。
  - 分支：默认不切分支，无论当前是 `main` / `master` 还是开发分支，都在当前分支完成已授权的动作；只有用户明确要求“切分支 / 新建分支 / 开 PR 分支”时才创建或切换，用用户给的名称，未给时用 `<type>/<kebab-描述>`（type 同提交类型，如 `feat/add-sector-ranking`、`fix/order-race-condition`）。
  - 评审交接：核对 SPEC 的 `验证计划`、`验证记录`，或本次会话中的交接信息。其中写明本次交付需要独立 Review（条件见 `spec` 的验证计划）却没有结论时，先交给独立 Review（默认 `open-code-review-delegate`），再继续 ship；证据仍覆盖相同内容与基线时复用，后续改动使其失效时重新交给独立 Review。两处都没有评审记录时，`ship` 不自行按条件评估，只在报告中写明“无评审记录”，不阻塞已授权的交付；用户要求评审时再交给独立 Review。评审只在独立阶段执行，第 3 步最终验证里不追加评审。
- 产出：交付范围、目标分支与 remote（或“仅本地”及原因）、评审交接状态。

### 2. 对齐远端（仅含推送）

- 做什么：`git fetch` 后比较目标分支与 `HEAD`；落后时先合入远端最新提交，再做最终验证，使验证覆盖将落到目标分支的集成结果。
  - 合入方式：沿用仓库约定；没有约定时，本地提交都未推送就 rebase，否则 merge，不改写已发布历史。分歧来自本地对已发布提交的 amend / rebase 时，不把被取代的旧提交合回来，按特殊说明的“强制推送”处理。
  - 工作区有未提交内容：用可恢复的非交互方式同步（如 `git pull --rebase --autostash`），恢复后检查 `git status` 与 diff；不能可靠保留用户变更时，暂停该动作并继续本地检查。
  - 冲突：出现未合并路径时，按 [references/merge-conflicts.md](references/merge-conflicts.md) 记录冲突集并逐文件处理（生成物重新生成、需求 ID 保持稳定、语义冲突自行合并并保留双方意图）；rebase 中 `ours` 通常是目标分支当前结果，`theirs` 才是正在重放的本地提交，不凭名称整文件选边。
- 产出：建立在目标分支最新提交之上的本地候选。

### 3. 最终验证

- 做什么：
  - 命令按优先级确定：① 匹配的 SPEC / PLAN 中已确认的命令；② 项目 `CLAUDE.md` 的“命令速查”（旧版为“项目质量门”）；③ 仓库已有 wrapper、package script、构建清单或 CI 入口中无歧义的命令；④ 仍无入口时完成可行检查并报告验证缺口，不猜其他技术生态的默认命令，也不把未经验证的行为报告为通过。
  - 范围：运行适用于受影响模块的静态检查、编译或聚焦测试；SPEC 或质量门要求，或涉及跨模块契约时，加完整回归 / 构建。最终质量门优先用非修改型命令（check、dry-run、test、build、verify）。纯文档 / skill 变更至少运行 `git diff --check` 和针对性过期引用搜索；改动已提交、工作区干净时，`git diff --check` 要对比目标分支（`git diff --check <目标分支>...HEAD`），否则检查的是空集。
  - 复用：仍覆盖相同文件状态、依赖和基线的有效证据可复用，内容变化后才重验；对齐或冲突处理带来的变化，重跑受影响检查。范围内的本地格式修复可自行完成，随后检查 diff 并重跑受影响检查，不需要回到别的阶段等待调用。
  - 核对：逐条确认验收标准（或直接请求的成功标准）都有实际改动和同层级证据；用户可见行为须有呈现层的值、状态或交互断言，不能只用数据层或 API 结果代替（口径见 `spec` 的 [references/acceptance.md](../spec/references/acceptance.md)）。必须解决本次改动引入的新问题，已有问题要明确区分。
- 产出：验证结果。

### 4. 文档收口

- 做什么：
  - 定位匹配 SPEC（依据当前任务、变更路径和 `list`，不通读历史正文）。验证 PASS 后：`文档状态` 设为 `已完成`，`最后更新` 改为当天，在 `验证记录` 追加最终验证的行（格式见下）；对应 PLAN 确认为 `已完成`；再运行 `list` 校验。发布版本未定时保留 `未定`，不为 ship 分配版本号。直接请求模式没有 SPEC / PLAN 时不创建，并在报告中说明不适用。

    ```markdown
    | YYYY-MM-DD | `实际命令` | PASS | 覆盖范围 |
    ```
  - 变更涉及架构、接口或数据模型时，按引用和 `list` 定位并同步对应文档，不为小改动遍历整个 `docs/`。
  - 入口内容：按 [claude-md-guide.md](../harness-init/references/claude-md-guide.md) 的「入口回写边界」，只执行用户明确要求的 `CLAUDE.md` 回写，或在报告中给出候选建议；变更涉及架构、接口或数据模型也不自动取得更新 `CLAUDE.md` 的权限，SPEC / PLAN 更新和已授权交付照常继续。
  - 仅在用户请求或项目规定本次交付要归档时，按 [references/archive.md](references/archive.md) 归档。
  - 文档同步产生新改动后，重跑适用的文档检查；改动了验证契约或可执行内容时，重跑受影响的质量门。
- 产出：状态一致的 SPEC / PLAN。

### 5. 提交

- 做什么：只在验证 PASS 后提交。暂存前查看 `git status --short --branch` 和 `git diff --stat`，只暂存本次范围内的文件，不夹带工作区里的其他改动。提交信息沿用仓库既有风格（看 `git log` 与项目约定）；没有可沿用的约定时，默认用 Conventional Commits 1.0.0：

  ```text
  <type>(<scope>): <subject>

  [Body: 为什么这样改、解决思路]

  [Footer: BREAKING CHANGE / Closes #issue / 宿主或项目要求的署名行]
  ```

  `type`：`feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `build` / `ci` / `chore` / `revert`。`subject`：中文祈使句（“新增”而非“增加了”），不加句号，不超过 50 字符，例如 `feat(market): 新增板块优先级评分与轮动分析`。
- 产出：提交。

### 6. 推送与 PR / MR（仅含相应授权）

- 做什么：推送前再次 `git fetch` 并比较目标分支；远端已推进就回到步骤 2 重新对齐并重验，最多两轮，仍被持续推进时保留本地候选、记录竞态并继续独立检查，不无限重试，也不反复要求批准。用普通 `git push` 推送到已确认的目标（无上游时 `git push -u <remote> <branch>`）。用户要求或仓库工作流规定创建 PR / MR 时，用环境中已认证的连接器或 CLI（`gh` / `glab`）创建；工具不可用时给出已准备好的标题、正文和创建链接，不声称已创建。
- 产出：推送结果，或 PR / MR。

## 产出要求

> 完成时可逐条核对的交付物与验收门；做事方式写在执行流程里。

最终以交付报告汇报，逐项包含：

- 验证：命令、退出码、PASS / FAIL 与覆盖范围，证据覆盖最终内容和基线。
- SPEC / PLAN 状态已按验证结果更新；直接请求没有匹配文档时，写明“不适用”。
- 评审交接：已核对的结论与覆盖范围，或交回独立 Review 的原因；没有评审记录时写明“无评审记录”。
- [仅归档时] 归档数量或 no-op。
- [含提交] Commit hash。
- [含推送] 对齐结果与推送前竞态复查的结果；推送目标。
- [含 PR / MR] PR / MR 链接。
- 未完成的检查、验证缺口，以及被跳过的步骤及原因。

## 特殊说明

> 跨步骤的策略与边界，每条带理由；只在单个步骤用到的规则写在该步骤里。

- **执行边界**：只读检索、本地草稿、可恢复的修改和常规本地检查直接推进；命名、实现细节和验证命令从代码与配置推断，关键假设写进产出；缺失的业务事实可一次性询问，同时继续不依赖答案的工作；会话中已给出的授权持续有效，已获授权的动作不重复确认，未获答复不等于授权。可恢复的事做错了可以重来，不可逆的事做错了无法挽回，所以只在“不可逆或难以恢复、且尚未获得授权”的动作前暂停：不执行该动作，其余工作照常，备好 diff / dry-run 与回退说明，并在报告中请求授权。本 skill 的暂停点：强制推送或改写已发布历史、不可恢复地丢弃冲突一侧的数据、授权范围之外的远端目的地。
- **强制推送**：改写远端历史不可逆，仅在用户明确要求时执行，不用裸 `--force`。分歧来自本地改写已发布的提交时：`git fetch` 后用 `git range-diff <merge-base> <远端分支> HEAD` 或 reflog 确认远端独有的提交都只是本地提交的旧版本，再用 `--force-with-lease=<分支>:<已核对的远端 SHA>` 推送，把租约钉在刚核对过的值上；远端含他人的提交（会被覆盖）或 SHA 已变化时不推送，报告原因。用户没有授权强制推送时，保留本地候选，报告分歧并请求授权，不用合并把旧提交带回来。其余情况一律普通 `git push`。

## 依赖脚本

| 脚本 / 工具 | 用途 | 调用与要求 |
|---|---|---|
| `scripts/spec_workflow.py` | 定位 SPEC、校验元数据 | 本 skill 内置副本（与 `spec` 的逐字节一致）：`python3 "<ship-skill-dir>/scripts/spec_workflow.py" list --root <项目根目录>`；Python 3.9+ |
| `scripts/archive_specs.py` | 归档已完成 SPEC（仅归档时用） | `python3 … --root <项目根目录> [--dry-run] [--force]`；Python 3.9+、Git；导入同目录 `spec_workflow.py` |
| `git` | 预检、对齐、暂存、提交、推送 | 必需 |
| `gh` / `glab` | 创建 PR / MR | 可选，仅在用户要求或仓库工作流规定创建 PR / MR 时使用，需已认证 |
