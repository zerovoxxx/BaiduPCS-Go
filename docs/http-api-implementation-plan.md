## 2 P0 冻结契约和行为基线

2026-11-02 已完成本阶段的文档、契约、示例、源码归属、离线基线和隔离兼容性探测；P0冻结时所有HTTP操作均为planned，当前实现状态见P1/P2章节。见 [P0 核对报告](http-api-p0-baseline.md) 和 [契约校验说明](../api/openapi/README.md)。

### 工作

1. 确认设计中的领域、DTO、路由 ID、所有权和配置生效规则。
2. 将设计目录转为 OpenAPI 3.1.1：每条路由都有输入、成功和错误响应、权限、幂等和能力条件；固定 operationId。
3. 保存 AST 生成的主项目业务清单，核对 CLI 34 个顶层命令、51 个命令节点、86 个参数和 132 个核心导出函数。此处计数不能代替逐项映射。
4. 记录当前 CLI 的关键行为：下载根目录和层级、上传 skip/overwrite/rsync、重试 0、空文件、断点恢复、转存 fs_id、整段分享文本、导出旧格式。
5. 只运行明确可离线的现有测试，网络测试先分类；记录主项目原有失败，不把它们与新改动混淆。
6. 验证 SQLite 驱动及 OpenAPI 工具在目标 Go 和交叉编译环境下的可用性，锁定最少依赖。

### 产物和验收

- 已交付 `api/openapi/openapi.yaml`：105 个 operation、89 个 path、190 个 schema；105 组 HTTP exchanges、67 个 schema 边界用例、25 组后续行为规格和 SSE 帧。
- 已交付 `source-inventory.json`：609 条 AST 记录均有映射；包含 45 个业务选项字段（补齐 OrderOptions），可通过 check_contract.py --write-inventory 重建。
- 原有离线测试在 Go 1.23.12/1.26.2 下各 14 个包通过；下载器测试编译失败及两个固定本地路径测试失败单列记录，真实百度未测。
- 所有命令参数均有等价字段、表达方式或不支持说明；没有未分类业务入口。
- 异步、分页、文件路径、整数编码、错误和 API principal 与百度账号的区分一致。
- 完整覆盖默认包括主项目所有有效业务；扩展和历史能力单列，不影响统计口径。

## 3 P1 建立运行基础和依赖边界

2026-11-02已完成本轮运行基础：五层代码落地，12个系统/配置操作可实际调用，race/真实HTTP契约/CLI回归及13目标构建通过。见[P1验证记录](http-api-p1-verification.md)与[启动指南](http-api-server.md)。

### 工作

1. 增加 `server` 子命令和 `internal/bootstrap`，集中组装依赖和信号处理；将 `main.init()` 的 cwd、旧配置初始化和退出副作用移入各模式的显式启动路径。
2. 建立领域错误、账号 ID、文件引用、有效传输选项等最小类型；按调用需求定义 ports。
3. 建立配置仓库和版本，覆盖 PCSConfig 全字段；实现 presence-aware PATCH 和默认值 schema。
4. 建立账号客户端工厂：从凭据和配置快照创建实例，避免借用 ActiveUser 和 CopyPCS 进行隔离。
5. 将 requester 的网络参数应用从进程共享可变状态收拢到客户端或 Transport 工厂；无法立即替换的部分由启动期固定，并禁止请求中热改。
6. 依据 P0 的 modernc.org/sqlite v1.38.2 候选建立 SQLite、秘密存储、数据目录锁和迁移版本；准备任务、事件和幂等表。初期 server 仅面向 darwin/arm64、darwin/amd64、linux/amd64、linux/arm64、windows/amd64；通过构建条件隔离驱动，使原有 CLI 目标仍可构建。
7. 实现 Bearer 认证、账号授权、请求 ID、日志脱敏、请求大小限制和错误输出。
8. 实现 SYS01 至 SYS04、SYS08 至 SYS09、CFG01 至 CFG05 和 CFG07；契约随程序内嵌，先提供真实的 planned/implemented 状态。
9. 建立短请求、SSE、内容代理三种期限策略和排空流程，避免把进程退出放进业务服务。

### 验收

- 无百度账号时服务仍能启动，健康和 readiness 含义清楚。
- false、0 和空代理字符串可被正确配置，非法配置不会部分生效；缺少 If-Match 返回 428，版本冲突返回 412；不把启动字段接入普通配置 PATCH。
- HTTP 层不直接 import pcscommand 或读取 pcsconfig.Config；应用层不 import HTTP 框架。
- 不同客户端工厂实例使用正确的账号和固定网络配置，不发生 Cookie、签名缓存串用。
- 进程关闭可以排空请求并关闭存储；业务代码不会调用 os.Exit。

## 4 P2 最小端到端验证

当前进度：P2-01—P2-12已收尾，生产server已装配账号、受限单文件HTTP、持久派发、轮询/控制、恢复及关闭。12个P1操作保持implemented；10个新开放操作为partial；83个仍planned。离线/race、实际HTTP schema、四个SIGKILL窗口和用户授权专用目录的真实百度上传回读、取消、重启恢复通过，见[P2记录](http-api-p2-verification.md)及[指南](http-api-p2-guide.md)。可以继续P3；partial不计为完整契约实现。

### 顺序和边界

1. P2a：导入规范化凭据、生成独立 account_id、加密持久化；读取脱敏账号，接入配置快照和 ClientFactory。不以百度 UID 去重，不读取 CLI 当前账号；完整账号管理、旧配置导入及交互登录不作为前置。
2. P2b：复用当前百度协议和真实上传/下载执行组件，先支持受控本地根目录、绝对网盘路径、单文件、明确选项。不得用复制文件的假执行器替代真实传输链路，也不提前迁移全部 CLI 命令。
3. 建立传输所需的最小持久任务：原子提交与幂等、有限并发和队列、任务查询、按任务取消、配置/凭据版本及检查点绑定。先使用轮询，不以 SSE、复杂调度策略或多级配额为前置。
4. P2c：停止服务保存已确认进度；重开将运行中任务置 interrupted。恢复前核验账号、目标、配置/凭据版本和源文件指纹；上传合并等远端结果未知时先核对，不能盲目自动重放。取消任务不等于关闭整个服务。
5. 最小链路验证后，按实际使用者需要确定 UploadEngine、DownloadEngine、JobControl、CheckpointStore 的边界；不预建空目录、通用工作流引擎或无使用者的接口。

UPL01、DWN01、JOB02/04/06/08 的受限路径在 P2 提前验证，完整契约仍分别在 P3/P4 验收。只支持部分选项时明确列出 supported_options及值/大小限制，其他请求返回 422；不得把整个 operation 标成完整实现。P2已按交接P2-01引入partial并同步路由、能力、schema、示例和校验器；固定选项值在supported_option_values中返回，资源上限见limits。受限HTTP已通过真实响应契约验收，完整操作仍在P3/P4核销。

P2交付、入库/派发故障窗口、HTTP映射、Cookie/HTTPS约束及生命周期证据见[核销表](http-api-p2-verification.md#逐项核销)；后续接入点以[工程交接](http-api-handoff.md)为准。

### 必须取得的证据

| 场景 | 验收结果 |
| --- | --- |
| HTTP 身份与账号 | Bearer 通过；两个账号及不允许的调用方不能串用凭据、任务或本地根目录 |
| 上传再下载 | 单文件经过实际百度适配器及现有执行组件，下载结果字节/摘要一致；无业务 stdout 或进程退出 |
| 取消 A | A 的网络/分片执行停止，B 继续，之后 C 能成功；终态不会被迟到事件覆盖 |
| 请求断开 | 已入库任务继续执行并可再次查询，不依赖提交请求的 context |
| 关闭与重开 | 使用同一数据目录，账号、配置和任务仍可读；从已确认检查点恢复，不将取消任务自动复活 |
| 检查点不匹配 | 账号、目标、凭据或源文件变化时拒绝恢复，不复用另一个任务的 uploadid/临时文件 |
| 提交/完成竞争 | 幂等提交只产生一个逻辑任务；远端完成而本地响应丢失时保留可核验的不确定状态 |

受控本地 HTTP/TLS 上游用于可重复验证真实执行链路、取消和故障，不计为百度实测。真实百度测试从 P2 开始，在显式配置的专用测试账号和目录运行；没有测试凭据时明确记为未测，不能用现有正常文件做测试，也不因此阻塞独立的离线工作。P7 汇总证据，不再是首次接入真实上游的阶段。

## 10 验证成本与变更规则

- 开发期只运行受影响的领域、服务、适配器和 HTTP 测试；涉及并发时运行相关 race 检查。
- 一个阶段收尾执行一次完整契约、既有离线回归和构建矩阵；只有新变更影响该结论时重跑。保留报告，不为不变代码重复交叉编译。
- 真实上游测试单列且显式启用；已知旧测试失败继续依据 P0 基线标记。
- 每个新增 port 必须有当前使用者，每个状态和持久化字段必须对应可执行场景。HTTP 不借用 pcsconfig.Config/pcscommand，应用层不依赖 HTTP 或百度客户端。
- P2 验证失败先修订边界和 planned 契约，再推进 P3；已实现 P1 不回退，也不继续扩展管理框架。

| P3（已交付） | 完整账号、分页/搜索/扫描、逐项结果、retry、持久事件/SSE和artifact | [P3逐项验收](http-api-p3-verification.md)，保留P2恢复与CLI读取回归 |
| P4 以后 | 完整传输及后续业务 | 每次依赖均来自已经验证的业务链路 |

## 12 当前默认决策

单服务实例、同 module、标准库 HTTP、SQLite、显式账号、长操作 job、凭据只写、受控本地根目录、静态 principal；不增加微服务、外部队列或工作流平台。五层表达职责和依赖，不要求每个简单操作穿过五个只转发的对象。

配置版本、CAS、持久化幂等和加密等已完成 P1 能力继续保留。全局硬上限和并发隔离先落实；调用方公平配额、复杂运维管理和便利会话后置。原 CLI 目标范围不缩减。
